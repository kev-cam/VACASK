# VACASK Digital Cosimulation — Architecture and Design

## 1. Purpose

This document describes the architecture of a transparent digital
cosimulation bridge between VACASK (analog circuit simulator) and
Icarus Verilog (digital event-driven simulator).  It is intended as a
design reference for reviewing the VACASK changes and the external
cosimulation module.

The goal is mixed-signal simulation: an analog circuit drives digital
logic (A2D) and digital outputs feed back into the analog domain (D2A),
with the two simulators running in a sampled co-simulation within a
single process.

The bridge is split into two pieces: a core (`cosim_core.cpp`) that
knows about VACASK — building the circuit, running its coroutine,
detecting threshold crossings, predicting breakpoints — and never
mentions any particular digital simulator; and a thin adapter
(`cosim_vpi_adapter.cpp` for Icarus) that implements a small
`DigitalSim` interface over that simulator's own native API. Only the
adapter needs to change to support a different digital simulator.

## 2. Roles and time mastering

VACASK is the **time master**.  Its adaptive transient engine chooses
timestep sizes based on LTE (local truncation error) control,
breakpoints, and convergence criteria.  The digital simulator is the
**time slave** — it advances its event clock to match each accepted
analog timestep.

This is the natural choice because:

- The analog solver's adaptive stepping is the bottleneck.  Digital
  event processing between two analog timesteps is effectively
  instantaneous.
- Analog convergence is sensitive to time-discretisation quality.
  Forcing it to stop at arbitrary digital event times would disrupt
  the predictor, increase rejected steps, and potentially cause
  "timestep too small" aborts.
- The digital domain can advance to any requested time on demand — it
  has no stability constraints on step size.

The disadvantage is that digital events that occur between two analog
timesteps are not seen until the next accepted point.  For signals
whose timing is derived from the analog domain (e.g. a clock
generated by an analog oscillator), this is not a problem — the
digital edge is created by the A2D threshold crossing, which is
already synchronised with the analog timestep (Section 6.1) and
forward-predicted (Section 10).  For signals generated purely in the
digital domain (e.g. a digital PLL feedback divider), the analog
solver has no way to know about them and cannot inject a breakpoint
for them.

## 3. Synchronisation mechanism

The two simulators run on separate execution stacks within the same
OS process, using POSIX `ucontext` stackful coroutines.  The digital
simulator drives the ping-pong by scheduling callbacks on its own
event queue rather than polling the analog side in a loop:

```
 ┌──────────────────────────┐     ┌──────────────────────────┐
 │  Icarus Verilog / VPI     │     │   VACASK transient loop  │
 │     (main_ctx stack)      │     │    (vacask_ctx stack)    │
 │                           │     │                          │
 │  $cosim_a2d / $cosim_d2a  │     │                          │
 │  $cosim_run ─────────────────>  build circuit, start tran  │
 │                           │     │         │                │
 │                     ◄──────────  yield at 1st accepted step│
 │  onAnalogTime(): writeBit │     │  (or a crossing within it)│
 │  wakeAfterSettle()        │     │         │                │
 │  onSettled(): readBit,    │     │                          │
 │    poke D2A Norton        │     │                          │
 │  wakeAt(next analog time) │     │                          │
 │       (cbAfterDelay) ────────>  resume, solve next step    │
 │                     ◄──────────  yield at next crossing     │
 │        ...                │     │         ...              │
 │                     ◄──────────  done=true (tran ended)     │
 │  finish()                 │     │                          │
 └──────────────────────────┘     └──────────────────────────┘
```

Each accepted step (and each interpolated crossing within it, see
Section 6.1) produces one `wakeAt()` request from the core, serviced by
the adapter via `vpi_register_cb(cbAfterDelay, ...)` — the actual
Verilog time advance is Icarus's own scheduler, not a manually computed
`#(dt)`. `wakeAfterSettle()` uses `cbReadWriteSynch`, which fires after
every event at the current timestamp has been processed, including
nonblocking updates, without advancing simulation time — this is how
the D2A side reads settled digital state before poking the Norton
source.

The ping-pong itself is implemented as:
- `swapcontext(&main_ctx, &vacask_ctx)` — Verilog yields to VACASK
- `swapcontext(&vacask_ctx, &main_ctx)` — VACASK yields to Verilog

Each `swapcontext` saves the caller's full register state and
restores the callee's.  This is cheaper than process-level IPC
(no kernel transitions, no serialisation), and both simulators
can access shared memory directly — no marshalling of solution
vectors or circuit parameters.

The VACASK context runs on a dedicated 8 MB stack allocated in static
storage.  This is large enough for deep NR solver recursion and
integrator coefficient computation.

### Why ucontext, not VACASK's built-in coroutine API

VACASK's `Analysis` class has a coroutine interface
(`start()`/`resume()`) based on C++20 coroutines (`co_yield`).
However, this coroutine yields at **sweep point boundaries**, not at
individual timesteps.  A single-point transient analysis completes its
entire timestep loop in one `resume()` call — it does not yield after
each accepted step.  The `onTimestepAccepted()` virtual hook, on the
other hand, fires at every accepted timestep inside the innermost
transient loop.  By using `ucontext` to yield from within this
callback, we get per-timestep synchronisation without modifying the
coroutine yield points or the transient loop structure.

## 4. Integration point: onTimestepAccepted()

The hook that bridges the two worlds is `TranCore::onTimestepAccepted()`,
a virtual method called inside the accepted-step branch of the main
transient loop in `coretran.cpp`:

```cpp
// Accept or reject
if (accept) {
    nPoints++;
    // ...write results, set progress...

    // Notify subclasses of the accepted point.
    if (!onTimestepAccepted(tSolve, hk, order)) {
        co_yield CoreState::Aborted;
    }

    // Store timestep (AFTER the callback)
    pastTimesteps.add(hk);

    // Advance time (AFTER the callback)
    tk = tSolve;

    // ...check finish/stop...

    // Advance history (AFTER the callback)
    solution.advance();
    states.advance();
}
```

This ordering is critical.  When the callback fires:

1. **The solution vector (`solution.data()`) holds the just-accepted
   values** — node voltages and branch currents at time `tSolve`.
   The A2D bridge reads these to determine digital input levels.

2. **`pastTimesteps` and `tk` have NOT been updated yet** — they
   still reflect the previous step.  A subclass (like PssTranCore)
   can read `getIntegCoeffs()` and `getPastTimesteps()` to see
   exactly the coefficients used to solve this step.

3. **History has NOT been advanced** — `solution.advance()` and
   `states.advance()` happen after the callback.  The D2A bridge
   can safely modify circuit parameters (current source values) via
   `setInstanceParameter()` before the next step begins.

The callback approach (`std::function<bool(double, double)>`) was
chosen over subclassing because:

- It does not require a new class in the inheritance hierarchy.
  `TranCore` is already subclassed by `PssTranCore` — adding a
  cosimulation subclass would risk diamond inheritance if PSS+cosim
  were ever combined.
- It is composable with regular transient analysis: multiple observers
  can be chained by wrapping.  Note: `PssTranCore::onTimestepAccepted()`
  overrides the base method without calling it, so the callback is
  currently not dispatched during PSS analysis.
- It keeps the cosimulation code entirely outside of VACASK's source
  tree — the callback is set externally via `setTimestepCallback()`.

Returning `false` from the callback aborts the transient analysis
(same contract as the existing virtual method).

## 5. Solution vector layout

The solution vector is a `VectorRepository<double>`, which inherits
from `CircularBuffer<Vector<double>>`.  Two methods on this class
have different meanings:

| Method       | Returns                                       |
|--------------|-----------------------------------------------|
| `size()`     | CircularBuffer depth (number of history levels, e.g. 5) |
| `length()`   | Vector element count (number of unknowns)     |

The accessors use `length()`, not `size()`.

The solution vector stores, in order:

| Index | Content                               |
|-------|---------------------------------------|
| 0     | Ground reference (always 0.0)         |
| 1..N  | Node voltages (potential, flow, internal unknowns) |
| N+1.. | Branch currents (voltage sources, inductors) |

`Circuit::unknownCount()` returns N (nodes + branches, excluding
ground).  `solutionLength()` returns N+1 (including ground at
index 0).

Node ordering is determined internally by VACASK after elaboration
(nodes are sorted and collapsed).  The only reliable mapping from
node names to solution indices is through `Circuit::findNode()` and
`Node::unknownIndex()`.

## 6. A2D bridge — analog to digital

The A2D bridge converts an analog node voltage to a digital logic
level using a Schmitt trigger (hysteresis comparator):

```
              vth_hi
  ─────────────┐
               │ → output = 1
               │
               │ (hysteresis band — output holds previous value)
               │
               │ → output = 0
  ─────────────┘
              vth_lo
```

Thresholds are supplied per port when it is bound (`$cosim_a2d(node,
reg, vth_lo, vth_hi)`), with no built-in default — the caller always
states them explicitly.  The hysteresis prevents chatter when the
analog voltage lingers near the threshold — a common problem with
simple comparators, especially on slowly-varying signals like
RC-filtered clocks.

The comparison itself runs in the core (`Core::onAnalogTime()`), which
writes the resulting bit directly to the bound Verilog register via
the adapter's `writeBit()`.  The register only changes value on an
actual threshold crossing, so its transitions are the real Schmitt
trigger edges, visible as such in a VCD waveform dump.

### 6.1. Crossing detection (linear interpolation)

Without crossing detection, digital edges are quantised to analog
timestep boundaries.  If the solver takes a 500 ns step that spans a
threshold crossing, the digital edge appears at the end of that step
rather than at the actual crossing time.

The crossing detection subsystem detects threshold crossings between
consecutive accepted timesteps and injects extra synchronisation
yields at the interpolated crossing times.  This is implemented
entirely in the core (`cosim_core.cpp`) — no modifications to the
VACASK solver are needed beyond the timestep callback itself.

**Algorithm** (runs inside `timestep_cb`, before the normal yield):

1. Read current voltages `curr[i]` for all A2D ports.
2. For each port, check if the voltage crossed a threshold since the
   previous accepted step:
   - Rising: `prev_v < vth_hi` and `curr >= vth_hi`
   - Falling: `prev_v > vth_lo` and `curr <= vth_lo`
3. For each crossing, compute the interpolated crossing time:
   ```
   frac = (vth - prev_v) / (curr - prev_v)
   t_cross = prev_time + frac * (tSolve - prev_time)
   ```
4. Sort crossings by time (handles multiple crossings in one step).
5. For each crossing, in time order:
   a. Compute interpolated voltages for ALL ports at `t_cross`.
   b. Assign the crossing port's own voltage to its threshold value
      exactly, not the interpolated one. Re-deriving it by
      interpolation lands within 1 ulp of the threshold on either
      side, which fails a `>=` comparison on roughly half of
      otherwise identical cycles — the crossing time was solved for
      that exact value, so there is no need for an epsilon nudge.
   b. Yield via `swapcontext` at `t_cross` with these voltages
      published; the adapter's scheduled callback resumes at that
      time, `onAnalogTime()` writes the resulting bit(s), and control
      returns to the core for the next crossing (or step 6).
6. After all crossing yields, do the normal yield at `tSolve` with
   the actual solution voltages.

**Multiple yields per timestep callback**: each crossing yield is a
`swapcontext(&vacask_ctx, &main_ctx)` from inside `timestep_cb`. This
means a single call to `onTimestepAccepted` can produce N+1
synchronisation points (N crossings + 1 normal) before returning to
the VACASK transient loop.  The VACASK solver is not aware of this —
it sees a single callback invocation.

**State tracking** (the `Crossing` struct in `cosim_core.cpp`):
- `prev_v[]` — previous accepted voltages (per port)
- `prev_time` — previous accepted time
- `ready` — false until the second accepted step (need two points
  for interpolation)
- `bp_pending[]` / `bp_time[]` / `bp_retries[]` — forward-prediction
  state, see Section 10
- `count` — total crossings detected (reported at finish)

**Narrow pulses**: if a signal rises above `vth_hi` and falls below
`vth_lo` within the same analog timestep, both crossings are detected
and yielded in time order — provided the solver actually took a step
landing on both sides of the pulse (see the narrow-pulse limitation in
Section 10).

### 6.2. Initial A2D state

The register bound to an A2D port is not initialised by the bridge. It
starts at Verilog's default `x` (unknown) and is set to its correct
value by the first `onAnalogTime()` call, scheduled once `$cosim_run`
starts the analysis and the solver accepts its first step.

This is deliberate.  If A2D registers were initialised to 0, a signal
that starts high in the analog domain (e.g. an active-low reset at
1.8 V) would undergo a false `0 → 1` transition before the first real
value arrives.  This creates spurious edges that can trigger
downstream flip-flops via race conditions in Verilog's event
scheduling.

By leaving A2D registers at `x`, the first write produces only an
`x → correct_value` transition. Note that in IEEE 1364, `x → 1` is a
posedge and `x → 0` is a negedge, so edge-triggered logic will see one
initial edge.  However, this is the *correct* edge for the signal's
actual state — it avoids a false intermediate `0 → 1` race that
explicit initialisation would create.

If the initial analog voltage is in the dead zone (between `vth_lo`
and `vth_hi`), the register stays at `x` until a definitive crossing
occurs — the same behaviour as an uninitialised flip-flop in a pure
digital simulation.

## 7. D2A bridge — digital to analog

### The problem with voltage sources

The obvious D2A approach — a DC voltage source whose value changes
at each timestep — causes solver failure.  The adaptive transient
engine uses a predictor (polynomial extrapolation from past solution
points) to estimate the next solution.  A voltage source that jumps
from 0 V to 1.8 V between two timesteps creates a discontinuity
that the predictor cannot track.  The result is:

1. The predicted solution is far from the actual solution.
2. The Newton-Raphson solver converges slowly or not at all.
3. The timestep controller shrinks `hk` to reduce LTE.
4. The step size collapses until the solver aborts with
   `TranError::TimestepTooSmall`.

### Norton equivalent: current source + R + C

The D2A bridge uses a Norton equivalent circuit instead:

```
         ┌─────────────────────────┐
         │                         │
    ┌────┴────┐   ┌────┐   ┌────┐ │
    │  I_d2a  │   │  R  │   │  C │ │
    │  (dc)   │   │     │   │    │ │
    └────┬────┘   └──┬──┘   └──┬─┘ │
         │          │          │    │
         └──────────┴──────────┘    │
                    │               │
                  node N          GND
```

- **Current source** (`isource`, type="dc"): its value is set via
  `setInstanceParameter("isrcN", "dc", I)` where `I = V_target / R`.
  Changing a current source's DC value only modifies the RHS
  (right-hand side) of the circuit equations — it does not alter the
  Jacobian matrix structure.  The node voltage responds smoothly.

- **Shunt resistor** (`r`, required, no default): defines the
  steady-state relationship V = I × R.  Also provides a DC path to
  ground for the node.

- **Smoothing capacitor** (`c`, optional — omitted if 0): creates an
  RC time constant (τ = R × C) that smooths step transitions.  The
  solver's predictor can track this smooth response without shrinking
  the timestep.

Both `r` and `c` are chosen by the caller per port when it binds
`$cosim_d2a(node, net, vdd, r, c)` — there is no built-in default.

The Norton components are instantiated by the core at `$cosim_run`
time, one set per D2A port, added to the toplevel scope. When one or
more D2A ports are declared, the analog netlist must load
`resistor.osdi` and `capacitor.osdi` (the latter only if any port uses
`c > 0`).  The bridge declares its private models (`__cosim_res`,
`__cosim_cap`, `__cosim_isrc`) against those device types but does not
load the `.osdi` files itself, to avoid the duplicate-load path in
`Circuit::add()`.

### Parameter injection

The current source value is updated via
`Circuit::setInstanceParameter()`, which writes directly to the
device instance's parameter struct (`DevSourceInstanceParams::dc`).
The built-in `isource` device reads this parameter in its `evalCore`
on the next evaluation — no `elaborateChanges()` call is needed. This
works because `isource` is a built-in device that reads its parameter
live; it is not a documented, general guarantee that any device
(including an OSDI one) can have its parameters changed mid-transient
— see the open question in Section 11.

A **local `Status` object** must be used for this call, not the
analysis's shared status.  If the shared status is used, an error
state from `setInstanceParameter` corrupts the running analysis.

### Steady-state accuracy

With the Norton equivalent, the steady-state voltage at the D2A node
(with no other load) is:

```
V_node = I × R = (V_target / R) × R = V_target
```

If the node has another load resistance, `R` forms a divider with it
and the achievable steady-state voltage is correspondingly lower; see
the qualification tests for worked examples. The voltage reaches
steady state after approximately 5τ.

## 8. Transparent interface

The user's Verilog modules are never modified by the bridge. A small,
hand-written top-level module (see `example/cosim_top.v` and each
qualification test's `cosim_top.v`) instantiates them and calls three
system tasks in an `initial` block:

```verilog
$cosim_a2d("<analog node>", <reg>,  vth_lo, vth_hi);  // one per A2D port
$cosim_d2a("<analog node>", <net>,  vdd, r, c);        // one per D2A port
$cosim_run("<netlist file>", tstop, tstep);
```

- `$cosim_a2d` binds an analog node to a digital register the core
  will write.  `vth_lo`/`vth_hi` are the Schmitt-trigger thresholds
  (Section 6).
- `$cosim_d2a` binds a digital net the core will read to an analog
  node, via a Norton source with the given `vdd`/`r`/`c`
  (Section 7).
- `$cosim_run` parses the netlist, builds the circuit, instantiates
  any D2A Norton sources, and starts the transient analysis with the
  given stop time and timestep. Call it last, after every
  `$cosim_a2d`/`$cosim_d2a` binding.

All three arguments to `$cosim_run` are plain numbers in SI base units
(seconds), so `tstop`/`tstep` are written as e.g. `2001e-6` rather than
with a suffix.

## 9. VACASK API surface

The cosimulation module uses four additions to VACASK's public API,
all in header files:

### 9.1. `TranCore::solutionValue(index)` / `solutionLength()`

```cpp
// coretran.h — public, inline, const
double solutionValue(size_t index) const {
    return (index < solution.length()) ? solution.data()[index] : 0.0;
}
size_t solutionLength() const { return solution.length(); }
```

Read-only accessors for the transient solution vector.  The `solution`
member is `protected` in `TranCore`; these provide bounds-checked
access without exposing the `VectorRepository` internals.

### 9.2. `TranCore::setTimestepCallback()`

```cpp
// coretran.h — public
using TimestepCallback = std::function<bool(double tSolve, double hk)>;
void setTimestepCallback(TimestepCallback cb) { timestepCallback_ = std::move(cb); }
```

Sets an optional callback that fires inside `onTimestepAccepted()`.
The callback receives the accepted time and step size.  Default
(no callback) is unchanged — `std::function` default-constructs to
empty.  This adds a `TimestepCallback` private member, which changes
`TranCore`'s object layout (ABI break — requires rebuilding
`libsimlib`).

### 9.3. `TranCore::setExternalBreakPoint()`

```cpp
// coretran.h — public
void setExternalBreakPoint(double t) {
    if (t > 0 && (externalBreakPoint_ < 0 || t < externalBreakPoint_))
        externalBreakPoint_ = t;
}
```

Lets the timestep callback request a breakpoint for a future time. The
solver will land at that time (or earlier, if some other constraint
already does) instead of stepping past it. Used for the
forward-prediction described in Section 10. Takes the minimum of any
previously set value and persists across steps until the solver
reaches or passes it (see `lib/coretran.cpp`, applied right after
`onTimestepAccepted()`).

### 9.4. `Tran::core()`

```cpp
// antran.h — public, inline
TranCore& core() { return tranCore; }
```

Exposes the `TranCore` from a `Tran` analysis object.  External code
holds an `Analysis*` from the factory and must `dynamic_cast<Tran*>`
to reach this accessor.

### What is NOT changed

- No modifications to the transient loop logic, NR solver, timestep
  controller, breakpoint handling, or output system.
- No new source files — only two existing headers and one existing
  `.cpp` are modified.
- No new dependencies.
- `onTimestepAccepted()` remains virtual and its default behaviour
  (return `true` when no callback is set) is preserved.

## 10. Known limitations

### Synchronisation model

This bridge uses a **sampled** cosimulation approach with
**forward-prediction**.  VACASK solves each analog interval before the
digital side sees the result.  To minimise the latency of this
approach, the timestep callback extrapolates each A2D voltage
trajectory (linear prediction from the last two accepted values) and
injects a solver breakpoint at the predicted threshold-crossing time.
This forces the solver to land at or near the crossing, so the digital
side sees the event within one sub-step of the actual transition.

If an injected breakpoint is reached or passed with no crossing firing
(the prediction was wrong — typically a linear extrapolation
undershooting a curved trajectory like an RC exponential), the port
re-arms and refines its prediction from the newer, better local slope,
up to a bounded number of retries per approach. This avoids both
giving up after one wrong guess and chasing a trajectory forever if it
never actually crosses.

For D2A paths smoothed by the Norton RC filter, the filter's time
constant absorbs any residual latency.

### Narrow-pulse detection

The crossing detector compares voltage endpoints of each accepted
interval, combined with forward-prediction breakpoints that force the
solver to land near predicted crossings.  This significantly improves
narrow-pulse visibility: if the slope at the current step predicts a
crossing, the solver will step to that time, making the pulse
endpoints visible.

However, a pulse that reverses direction within a single step (both
endpoints below `vth_lo` with no breakpoint forcing subdivision) is
still invisible.  This can happen when analog sources do not produce
solver breakpoints and the pulse width is much shorter than the
adaptive timestep.

No test in `qualification/` exercises a narrow pulse without source
breakpoints, because such a stimulus cannot be constructed from
VACASK's current primitive set (no inductor model; all source waveform
types insert corner breakpoints; the D2A path can only change state at
an accepted timestep).  This limitation is documented rather than
measured.

### Platform

The bridge requires POSIX `ucontext` (Linux/macOS).  Windows is
not supported.

## 11. Open questions

### OSDI parameter changes mid-transient

`setInstanceParameter()` is used to poke the D2A Norton current
source's `dc` value at every yield (Section 7). This currently works
because `isource` is a VACASK built-in that reads its parameter struct
live on every evaluation. Whether this is meant to work in general for
OSDI-backed devices is not established:
`setInstanceParameter()` sets a `HierarchyParametersChanged` flag that,
as far as this bridge's testing goes, is only consumed by
`elaborateChanges()`, which runs before an analysis starts and not
during the transient loop. If OSDI devices are not meant to have
parameters changed mid-analysis, that is a constraint on what D2A can
poke, not a bug in this bridge — but it is worth confirming with
whoever owns that part of VACASK.

### Digital events not derived from the analog domain

Digital events generated purely in the digital domain (not derived
from analog crossings) are not fed back as analog breakpoints — the
analog side has no way to know about them in advance. For the D2A
direction this is not a problem in practice: changes are applied via
`setInstanceParameter` at each yield, and the Norton RC filter smooths
the transition regardless of exactly when within an analog step the
digital side changed state.

### Multi-bit buses

The current bridge handles single-bit ports.  Multi-bit buses
(e.g. an 8-bit DAC input) would require either one D2A port per bit
or a weighted Norton source.  Not implemented.
